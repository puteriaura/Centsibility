# Implementation Plan: Centsibility Critical Fixes & Enhancements

Based on your updated screenshots and requirements, here is the plan to address the most critical security issues first, followed by the recruitment flow and investment features. I will apply these incrementally so we can verify them step by step.

## Proposed Changes

### Phase 1: Critical Security (PIN & Email)

#### 1. Commander PIN Security Fix
Currently, if the parent's Supabase session is still active in the browser, a child clicking "Parent" can bypass to the dashboard if a PIN hasn't been set yet (triggering the "Set PIN" screen).
**Fix**:
- In `login.tsx`, flag when a parent logs in with a password (`sessionStorage.setItem('justLoggedIn', 'true')`).
- In `parent.tsx` (the PIN screen), if a PIN is *not* set, check this flag.
- If the flag is missing (meaning they bypassed from the Kid view), immediately log them out and redirect to the login screen with a security message: *"Please log in with your password to set your Commander PIN."*
- Add a **Back Button** on the PIN screen.

#### 2. Email Uniqueness (Parent Accounts)
Supabase Auth enforces email uniqueness, but to provide immediate feedback during registration:
**Fix**:
- In `login.tsx` (Signup mode), before calling `signUp`, query the `profiles` table to check if the email already exists.
- If it does, show error: *"An account with this email already exists. Please sign in."*.

### Phase 2: Child Recruitment UI & Validation

#### 3. Recruitment Flow & Duplicate Names
- **UI Update**: In `parent.index.tsx`, hide child name and `@username` fields by default. Add a prominent **"+ RECRUIT ANOTHER ASTRONAUT"** button that reveals the form.
- **Validation**: In `parent.functions.ts` (`parentCreateKid`), add a check to ensure the new child's name does not match any existing child name under the same parent.

### Phase 3: Investment Feature Overhaul (Kids Control)

#### 4. Investment Overhaul
- **Storage Strategy**: Store investment preferences (Risk & Frequency) inside the unused `bio` field of the `kids` table as a JSON string (e.g., `{ "risk": "High", "freq": "Daily" }`).
- **Kid UI**: Update `kid.invest.tsx` to let the child choose Risk (Very Low to Very High) and Frequency (Every Minute to Monthly).
- **Simulation**: Modify `kidInvestSettle` server function to apply randomized growth/loss based on the selected risk profile when the frequency threshold is met.

> [!IMPORTANT]
> **Open Question**: Are you okay with storing the Investment preferences inside the `bio` field to avoid database schema changes?

If this plan looks good, I will begin executing Phase 1 (PIN Security & Email Uniqueness).

# Architectural Refactor: Migrating to Supabase Edge Functions

This plan outlines the steps to migrate all privileged server-side logic from the client-side shim (`src/server/*.functions.ts`) to proper Supabase Edge Functions, resolving the critical security flaw identified in the audit.

## Goal Description

Eliminate the faux server function layer (`createServerFn`) that runs admin logic in the browser. Instead, move all mutations requiring elevated permissions (using the Service Role Key) into Supabase Edge Functions (`kid-finance`, `parent-finance`, and potentially a new `auth` function). The frontend will be updated to securely invoke these edge functions using JWTs and session tokens.

## User Review Required

> [!CAUTION]
> **Supabase Deployment:** This refactor will create/update Deno Edge Functions in the `supabase/functions/` directory. Once the code changes are made, these functions must be deployed to your Supabase project using the Supabase CLI (e.g., `supabase functions deploy`). You will also need to securely set the `SUPABASE_SERVICE_ROLE_KEY` in the Edge Function environment variables.
> 
> **Are you comfortable running the Supabase CLI to deploy these functions after I write the code?**
